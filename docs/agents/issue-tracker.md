# Issue Tracker

GitHub Issues in `paularg/zara-challenge-inditex` are the source of truth for
tracked work. Read this document before creating, updating, prioritizing, or
closing an issue.

## Workflow

1. Search open and closed issues before creating one. Continue an existing
   issue when it already represents the same outcome.
2. Create or mutate issues only when the user has asked for that external
   change. Keep exploratory notes in the current task until tracking is
   authorized.
3. Write each issue so another contributor can complete it without relying on
   conversation history.
4. Record dependencies with direct issue links and state whether they block the
   work. Work on unblocked issues first.
5. Close an issue only after every acceptance criterion is satisfied and its
   validation evidence is recorded.

## Issue contract

Use a concise, outcome-oriented title and include these sections when they are
relevant:

- **Context** — Why the work exists and the current observable behavior.
- **Outcome** — The user-visible or architectural result to deliver.
- **Acceptance criteria** — A checkable list that defines completion.
- **Validation** — Commands or manual checks that prove the outcome.
- **Dependencies** — Blocking issues, external decisions, or `None`.

Treat labels, milestones, and assignees as repository state: inspect the current
options before using them, and add new taxonomy only when the user requests it.
Preserve Product-domain vocabulary from `CONTEXT.md` and repository standards
from `docs/conventions.md` in every issue.
